# Pausing and resuming production

**Code as of:** `c9debed` · account read 2026-11-07

The runbook for switching the production backend off to save money and back on
again **without deleting anything**. Every command runs from Git Bash in the repo
root, as Arpan, with the SSO profile signed in. A session cannot run the write
commands itself: `scripts/hooks/guard-aws.mjs` refuses them, so they go in the
prompt with a leading `!`.

## In one paragraph

Two things cost money by the hour and can be switched off: the one EC2 instance
running the backend (`t3.small`) and the RDS database (`db.t4g.micro`). The
instance is switched off by setting its **Auto Scaling group** to zero, so the
Elastic Beanstalk environment, its Elastic IP, the CloudFront distribution, the
HTTPS certificate and `api.campusvibe-mcgill.com` all stay in place. The
database is **stopped**, which keeps its data, password and backups. Resuming is
the same steps reversed: **schedule off, database, then the instance.**

Since 2026-11-07 there is no load balancer: the environment is a single instance
behind CloudFront ([ADR-017](../decisions/ADR-017-api-https-through-cloudfront-not-a-load-balancer.md)).

## What the pause saves

load balancer; the Elastic IP and CloudFront are AWS list prices.

| Item | Running | Paused |
|---|---|---|
| EC2 `t3.small` + its disk | ~$17 | $0 |
| Elastic IP `3.97.216.208` | ~$3.65 | ~$3.65 — **billed attached or not** |
| RDS `db.t4g.micro` | ~$14 | ~$2.50 (20 GB storage only) |
| CloudFront | $0 within the free tier | $0 |

## Step 0 — sign in

```bash
aws sso login --profile campusvibe-admin
export AWS_PROFILE=campusvibe-admin
aws sts get-caller-identity
```

- `aws sso login` opens the browser and fetches temporary credentials.
- `export AWS_PROFILE=...` makes every later `aws` call in this terminal use them,
  so `--profile` can be left off. Never use the `default` profile: it holds a dead
  key (`.claude/rules/aws-handling.md`).
- `sts get-caller-identity` prints the account (`172644092604`) and role. If it
  errors, the login did not take.

## Pause

```bash
# 1. Backend instance -> 0
aws autoscaling update-auto-scaling-group --region ca-central-1 \
  --auto-scaling-group-name awseb-e-ep7prttpws-stack-AWSEBAutoScalingGroup-ammKwECv66cf \
  --min-size 0 --max-size 0 --desired-capacity 0

# 2. Database -> stopped
aws rds stop-db-instance --region ca-central-1 \
  --db-instance-identifier campusvibe-prod-db

# 3. Daily re-stop schedule -> on (the full command is under Resume, with
#    --state ENABLED instead of DISABLED)
```

What each flag means:

- `--desired-capacity` is how many instances the group runs right now;
  `--min-size` and `--max-size` are the bounds it may scale between. All three go
  to 0 so nothing starts a replacement.
- The group is changed **directly**, not through Elastic Beanstalk option
  settings. An option-setting change is an environment update, and an
  environment update can put back the `0.0.0.0/0` port 80 rule that the manual
  CloudFront-only rule replaced (`rules/aws-handling.md`).
- `stop-db-instance` shuts the database down; storage and automated backups stay.
- The Elastic IP stays allocated with no instance, so the environment CNAME —
  CloudFront's origin — keeps its address for resume.

Expect the Elastic Beanstalk environment to turn **Grey** in the console and the
API to **hang about 30 s, then answer a CloudFront 504** — CloudFront retries
the stopped origin before giving up. Both are correct while paused. The Vercel
frontend still loads, but every call to the backend fails.

### The 7-day catch, handled by a daily schedule

**AWS starts a stopped RDS instance again by itself after 7 days**, and it starts
billing again. Since 2026-11-07 an EventBridge Scheduler schedule stops it again
every day, so it runs at most about a day after an automatic start.

| Thing | Value |
|---|---|
| Schedule | `campusvibe-stop-rds-daily`, `ca-central-1`, default group |
| When | `cron(0 3 * * ? *)`, `America/Toronto` — 03:00 daily |
| Target | universal target `arn:aws:scheduler:::aws-sdk:rds:stopDBInstance`, input `{"DbInstanceIdentifier":"campusvibe-prod-db"}`, 0 retries |
| Role | `CampusVibe-Scheduler-StopRDS` — trusts `scheduler.amazonaws.com` for account `172644092604` only; inline `StopCampusVibeProdDb` allows only `rds:StopDBInstance` on `campusvibe-prod-db` |
| Cost | $0 — within the Scheduler free tier |

Daily rather than weekly because a weekly run can land just before the
auto-start and miss it by six days, at the same cost. On days the database is
already stopped the call fails with `InvalidDBInstanceState`; that is expected
and is why retries are 0.

Re-create it if it is ever deleted (the JSON is the table above):
`iam create-role`, `iam put-role-policy`, then `scheduler create-schedule
--target file://target.json`.

Check the database with:

```bash
aws rds describe-db-instances --region ca-central-1 \
  --db-instance-identifier campusvibe-prod-db \
  --query "DBInstances[0].DBInstanceStatus" --output text
```

`stopped` is good; `available` means it woke up — the schedule stops it by the
next 03:00, or run the stop command now.

## Resume

**First disable the re-stop schedule**, or it stops the live database at the
next 03:00. `update-schedule` replaces the whole schedule, so every field is
passed again:

```bash
aws scheduler update-schedule --region ca-central-1 \
  --name campusvibe-stop-rds-daily \
  --schedule-expression "cron(0 3 * * ? *)" \
  --schedule-expression-timezone America/Toronto \
  --flexible-time-window Mode=OFF \
  --target '{"Arn":"arn:aws:scheduler:::aws-sdk:rds:stopDBInstance","RoleArn":"arn:aws:iam::172644092604:role/CampusVibe-Scheduler-StopRDS","Input":"{\"DbInstanceIdentifier\":\"campusvibe-prod-db\"}","RetryPolicy":{"MaximumRetryAttempts":0}}' \
  --state DISABLED
```

To pause again later, run the same command with `--state ENABLED`.

Then the database and the backend. Order matters: the backend runs Flyway
against the database at startup and fails if the database is not there yet.

```bash
# 1. Database -> running, and wait until it is ready (takes a few minutes)
aws rds start-db-instance --region ca-central-1 \
  --db-instance-identifier campusvibe-prod-db
aws rds wait db-instance-available --region ca-central-1 \
  --db-instance-identifier campusvibe-prod-db

# 2. Backend instance -> 1
aws autoscaling update-auto-scaling-group --region ca-central-1 \
  --auto-scaling-group-name awseb-e-ep7prttpws-stack-AWSEBAutoScalingGroup-ammKwECv66cf \
  --min-size 1 --max-size 1 --desired-capacity 1
```

- `aws rds wait ...` returns nothing until the database is `available`, then
  exits. If it times out, run it again. A session cannot run it: the guard hook
  refuses every `wait` verb, so a session polls `describe-db-instances` instead.
- The new instance boots, pulls the current application version and starts the
  container; allow about 5–10 minutes. On 2026-11-07 it was Green in about 2.

### Check it came back

```bash
# Environment health: want Ready / Green
aws elasticbeanstalk describe-environments --region ca-central-1 \
  --environment-names CampusVibe-Backend-Prod \
  --query "Environments[0].[Status,Health]" --output text

# The instance holds the Elastic IP
aws ec2 describe-addresses --region ca-central-1 \
  --query "Addresses[].[PublicIp,InstanceId]" --output text

# Port 80 still admits only CloudFront: want pl-38a64351 and no 0.0.0.0/0
aws ec2 describe-security-groups --region ca-central-1 \
  --group-ids sg-0e9453ad8fbde508e --query "SecurityGroups[0].IpPermissions"

# End to end, through CloudFront
curl -s https://api.campusvibe-mcgill.com/actuator/health
```

`{"status":"UP"}` from the last command means production is back.

### If it does not come back

- **A CloudFront 502 or 504** — the origin is unreachable or slow: the instance
  is not running yet, the container failed, or the port 80 rule is missing.
- **Failed to fetch in one browser while `curl` works** — that browser holds an
  old DNS answer for `api`. Clear `chrome://net-internals/#dns`, flush the
  socket pools on `#sockets`, and run `ipconfig /flushdns`.
- **The container exits on start** — read its log. The stream name is the
  instance id:

  ```bash
  export MSYS_NO_PATHCONV=1
  aws ec2 describe-instances --region ca-central-1 \
    --filters Name=instance-state-name,Values=running \
    --query "Reservations[].Instances[].InstanceId" --output text
  aws logs get-log-events --region ca-central-1 \
    --log-group-name /aws/elasticbeanstalk/CampusVibe-Backend-Prod/var/log/eb-docker/containers/eb-current-app/stdouterr.log \
    --log-stream-name <instance id> --limit 100
  ```

  A database connection error usually means step 1 had not finished; wait for
  `available`, then terminate the instance in the console so the group starts
  a fresh one.

## While paused: do not deploy

An Elastic Beanstalk deploy with zero instances has nowhere to land. Resume first
(the group back to 1/1/1), then deploy the new `package-eb.mjs` bundle.

## Not done here

- **Terminating the environment** would bring the floor from ~$6 to ~$3 a month,
  by releasing the Elastic IP. Weighed and dropped 2026-11-07 for ADR-017, which
  removed the load balancer's ~$25 without deleting anything. Termination costs
  more than it saves: no saved configuration exists, so every environment
  property and secret would be lost; `campusvibe-database-sg` admits only the
  environment's own security group, so termination fails on that reference
  unless the rule is removed first; and the environment CNAME, which is
  CloudFront's origin, would be released.
