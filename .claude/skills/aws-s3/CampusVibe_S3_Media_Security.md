# CampusVibe S3 Media Security and Presigned URL Implementation

## Purpose

This document defines the production security model and implementation rules for storing and serving CampusVibe media through AWS S3.

It is intended for Claude Code and should be treated as the source of truth for:

- S3 access control
- IAM permissions
- media upload authorization
- presigned upload URLs
- presigned download/view URLs
- object-key generation
- database storage
- file validation
- file deletion/replacement
- AWS credential handling
- future Elastic Beanstalk integration

Do not weaken these controls for convenience.

---

# 1. Current AWS State

The following infrastructure already exists:

```text
AWS Region:
ca-central-1

S3:
Private production media bucket

Bucket characteristics:
- General purpose bucket
- Block Public Access enabled
- ACLs disabled
- Bucket Owner Enforced
- SSE-S3 encryption
- Object Lock disabled
- Versioning currently disabled
- Production CORS configured

IAM policy:
CampusVibeProdMediaS3Access

Current policy state:
Unattached until the Elastic Beanstalk backend IAM role exists
```

The production S3 bucket must remain private.

---

# 2. Final AWS Access Model

The production access model must be:

```text
CampusVibeAdmin
    |
    | AdministratorAccess
    | human infrastructure management only
    v

Elastic Beanstalk
    |
    v
EC2 instance
    |
    | assumes
    v
CampusVibe backend IAM role
    |
    | has
    v
CampusVibeProdMediaS3Access
    |
    v
PRIVATE S3 BUCKET
```

Browser access to S3 must happen only through temporary presigned URLs generated by the backend.

```text
Browser
   |
   | authenticated CampusVibe request
   v
Spring Boot
   |
   | authorization check
   | creates short-lived presigned URL
   v
Browser ----------------------> S3
         direct temporary access
```

There must be no permanent AWS credential in the browser or application source code.

# 3. IAM Responsibilities

## Human administrator

`CampusVibeAdmin` is the human AWS administrator.

It may:

- create and configure AWS resources
- create IAM roles and policies
- manage RDS
- manage S3
- manage Elastic Beanstalk
- manage Secrets Manager
- manage CloudWatch
- manage networking/security groups

The application must never inherit `CampusVibeAdmin` permissions.

## Application IAM role

When Elastic Beanstalk is created, its EC2 instances must use a dedicated IAM instance role.

That role should receive the existing policy:

```text
CampusVibeProdMediaS3Access
```

Do not attach `AdministratorAccess` to the application role.

Do not use an IAM user for the application.

Do not generate static AWS access keys for the backend.

---

# 4. Required S3 IAM Policy

The backend application should initially have only:

```text
s3:GetObject
s3:PutObject
s3:DeleteObject
```

against the production media bucket's objects.

Example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CampusVibeMediaObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::campusvibe-prod-media-ca/*"
    }
  ]
}
```

Replace the bucket name with the actual production bucket name.

Do not use:

```json
"Action": "s3:*"
```

Do not use:

```json
"Resource": "*"
```

Do not add `s3:ListBucket` unless a concrete backend feature requires it.

The application should retrieve objects by known object key stored in PostgreSQL rather than listing/searching the bucket.

---

# 5. AWS Credential Rules

The Spring Boot backend must use the AWS SDK default credential provider chain.

Production credentials should be obtained automatically from the EC2 instance role.

Do not configure:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

for the production application.

Do not put AWS keys in:

- `.env`
- `application.yml`
- `application-prod.yml`
- Dockerfile
- Docker Compose
- GitHub repository
- Vercel
- frontend environment variables
- database
- source code

Local development may use a separate secure developer mechanism if needed, but production must use IAM roles.

---

# 6. S3 Bucket Rules

The production media bucket must remain:

```text
Public access:
BLOCKED

ACLs:
DISABLED

Object ownership:
Bucket Owner Enforced

Encryption:
SSE-S3

Application access:
IAM role only

Browser access:
Presigned URLs only
```

Never make the bucket public to make event or profile images easier to display.

Never assign `public-read` ACLs.

Never add a public bucket policy.

# 7. Media Object Structure

Use stable resource-oriented prefixes.

Recommended structure:

```text
clubs/
  {clubId}/
    logos/
      {uuid}.webp

events/
  {eventId}/
    banners/
      {uuid}.webp

users/
  {userId}/
    profiles/
      {uuid}.webp
```

Examples:

```text
clubs/24/logos/2ea3bc64-26fd-4aa8-bc30-71598de7cb18.webp

events/381/banners/97b3dd6a-c410-4c26-b815-d1964b9455bd.webp

users/840/profiles/60acb063-d44b-4496-b8cc-08470fe7e9c2.webp
```

The backend must generate object keys.

Never let a client provide an arbitrary full S3 object key.

---

# 8. Database Storage

PostgreSQL should store S3 object keys, not permanent S3 URLs.

Prefer:

```text
events.banner_object_key
clubs.logo_object_key
users.profile_image_object_key
```

Example value:

```text
events/381/banners/97b3dd6a-c410-4c26-b815-d1964b9455bd.webp
```

Do not store:

```text
https://bucket-name.s3.amazonaws.com/...
```

unless there is a compelling architectural reason.

Storing object keys allows CampusVibe to later change delivery from:

```text
S3 presigned GET URLs
```

to:

```text
CloudFront
```

without rewriting stored database data.

---

# 9. Presigned Upload Flow

User uploads must use backend-authorized presigned PUT URLs.

Target flow:

```text
1. Browser requests upload permission

POST /api/...

2. Spring Boot authenticates user

3. Spring Boot authorizes resource ownership

4. Spring Boot validates upload metadata

5. Spring Boot generates object key

6. Spring Boot generates short-lived presigned PUT URL

7. Backend returns:
   - upload URL
   - object key or upload token if needed
   - required headers

8. Browser uploads directly to S3

9. Application confirms/saves media association
```

Example:

```text
Club admin
   |
   | POST /api/events/381/banner/upload-url
   v
Spring Boot
   |
   | verify authenticated
   | verify user can manage event 381
   | validate image type/size intent
   | generate object key
   v
Presigned PUT URL
   |
   v
Browser -----------------------> S3
```

---

# 10. Upload Authorization Rules

A presigned URL must never be generated before authorization succeeds.

Examples:

## Club logo

The user must be an authorized admin of that club.

## Event banner

The user must be an authorized admin of the club that owns the event.

## User profile image

The authenticated user may upload only for their own profile unless an explicit admin workflow permits otherwise.

Never trust IDs from the client alone.

For example:

```text
POST /api/events/381/banner/upload-url
```

must verify:

```text
event 381 exists
AND
event 381 belongs to club X
AND
current user is authorized to manage club X
```

before generating an S3 upload URL.

---

# 11. Presigned Upload URL Lifetime

Upload URLs must be short-lived.

Recommended:

```text
5-15 minutes
```

Prefer approximately:

```text
10 minutes
```

unless there is a concrete UX reason to change it.

Do not generate URLs lasting hours or days for normal uploads.

---

# 12. Upload Validation

At minimum validate:

```text
Allowed file types:
image/jpeg
image/png
image/webp
```

Recommended maximum size:

```text
5 MB
```

Adjust only if product requirements require larger files.

Validate:

- authenticated user
- authorization
- intended media type
- expected MIME type
- maximum size
- associated resource
- generated object path
- allowed file extension

Do not trust only:

```text
filename
Content-Type
file extension
```

provided by the browser.

Where practical, verify the actual uploaded file after upload or through an image-processing pipeline.

---

# 13. Filename Rules

Do not use user-supplied filenames as the canonical S3 object name.

Avoid:

```text
events/381/banner/my-event-image-final-final.png
```

Prefer:

```text
events/381/banners/{uuid}.webp
```

Benefits:

- prevents collisions
- avoids unsafe filenames
- removes path traversal concerns
- simplifies replacement
- avoids exposing user-local filenames
- provides predictable key structure

---

# 14. Image Format Strategy

CampusVibe should preferably normalize application images to web-friendly formats.

Preferred output:

```text
WebP
```

where the current image-processing architecture supports it.

Possible workflow:

```text
original upload
   |
validation
   |
optional resize/compression
   |
WebP output
   |
S3
```

Do not block initial deployment on advanced image processing if it does not already exist.

Security and authorization take priority over format optimization.

---

# 15. Presigned Read/View URLs

Because the S3 bucket is private, direct public S3 URLs should not be used.

Initial recommended read model:

```text
Frontend
   |
   | requests CampusVibe data
   v
Spring Boot
   |
   | retrieves object key from PostgreSQL
   | generates short-lived presigned GET URL
   v
Frontend
   |
   v
S3
```

Example API response:

```json
{
  "id": 381,
  "name": "Tech Career Fair",
  "bannerUrl": "https://temporary-presigned-s3-url..."
}
```

Do not expose AWS credentials.

---

# 16. Presigned GET URL Lifetime

Read URLs may last longer than upload URLs because they are used for display.

A reasonable initial range is:

```text
15-60 minutes
```

Recommended starting point:

```text
30 minutes
```

The exact value may be adjusted based on caching and user experience.

Do not persist the generated presigned URL in PostgreSQL.

Generate it from the stored object key when returning API data.

---

# 17. Public Media vs Private Bucket

CampusVibe event banners, club logos, and profile images may be viewable by users of the application, but the bucket itself should still remain private.

These are different concepts:

```text
Application-visible media
!=
Public S3 bucket
```

The application controls access by issuing temporary URLs.

Initial architecture:

```text
Browser
   |
   v
Spring Boot
   |
   | temporary GET URL
   v
Private S3
```

Later, if traffic becomes substantial:

```text
Browser
   |
   v
CloudFront
   |
   | Origin Access Control
   v
Private S3
```

Do not introduce CloudFront during the initial deployment unless explicitly requested.

---

# 18. Upload Completion Handling

A presigned URL only authorizes the upload.

The application still needs to decide when the uploaded object becomes the active media object for a resource.

Recommended design:

```text
1. Backend creates object key and upload URL
2. Browser uploads object
3. Browser calls confirmation endpoint
4. Backend verifies object metadata/existence if appropriate
5. Backend updates PostgreSQL
6. Old object is deleted if replacing existing media
```

Example:

```text
POST /api/events/381/banner/confirm
```

The exact endpoint design may vary, but database state should not claim an upload exists before the application has sufficient confirmation.

---

# 19. Replacement Behavior

When replacing an existing image:

```text
Existing:
events/381/banners/old-uuid.webp

New:
events/381/banners/new-uuid.webp
```

Recommended sequence:

```text
1. Upload new image
2. Validate/confirm new image
3. Update database to new object key
4. Delete old S3 object
```

Do not delete the old object before the new upload succeeds.

This avoids broken images if an upload fails.

---

# 20. Delete Behavior

When application data is deleted, media cleanup must be explicit.

Examples:

```text
delete club
delete event
remove profile image
replace event banner
replace club logo
```

The backend should delete associated obsolete S3 objects using:

```text
s3:DeleteObject
```

Do not rely on users to delete objects.

Do not list the entire bucket to discover related objects if object keys are already stored in PostgreSQL.

---

# 21. Database Transaction Considerations

S3 and PostgreSQL are not part of one ACID transaction.

Claude Code must account for partial failure.

Example:

```text
S3 upload succeeds
but
database update fails
```

This may leave an orphaned object.

Likewise:

```text
database update succeeds
but
S3 delete fails
```

This may leave an obsolete object.

For the initial implementation:

- keep operations ordered safely
- log cleanup failures
- make delete operations retryable/idempotent where practical
- avoid making a failed S3 cleanup break unrelated core data
- consider a periodic orphan cleanup job only if orphan accumulation becomes a real issue

Do not add complex distributed transaction infrastructure.

---

# 22. Security Logging

Log:

- resource ID
- media operation type
- authenticated user ID
- generated object key
- success/failure
- authorization denial
- S3 operation failure

Do not log:

- presigned URL query signatures
- AWS credentials
- authorization headers
- JWTs
- secret values

Presigned URLs contain temporary authorization information and should be treated as sensitive while valid.

---

# 23. CORS

S3 CORS is already configured.

Production CORS must remain limited to approved CampusVibe frontend origins.

Do not use:

```json
"AllowedOrigins": ["*"]
```

when the production origins are known.

Expected methods for the current design:

```text
GET
PUT
```

Add methods only when required.

CORS does not provide authorization.

Authorization must still be enforced by the backend before it generates a presigned URL.

# 24. Spring Boot AWS SDK Configuration

Use AWS SDK for Java.

Production client creation should rely on:

```text
AWS_REGION=ca-central-1
```

and the default AWS credential provider chain.

Conceptually:

```java
S3Client.builder()
    .region(region)
    .build();
```

and the appropriate presigner:

```java
S3Presigner.builder()
    .region(region)
    .build();
```

Do not provide hard-coded access keys through a static credentials provider.

# 25. Application Configuration

Non-secret configuration:

```text
AWS_REGION=ca-central-1
S3_BUCKET=<actual-production-bucket-name>
```

These may be Elastic Beanstalk environment properties.

Do not put the bucket name or region into frontend configuration unless the frontend specifically needs them.

The frontend should generally deal only with API responses and presigned URLs.

# 26. Suggested Backend Service Boundary

Prefer a dedicated media/S3 abstraction rather than calling AWS SDK methods throughout controllers.

Example responsibility split:

```text
MediaController
    |
    v
MediaService
    |
    +-- authorization/resource checks
    +-- file metadata validation
    +-- object key generation
    +-- upload workflow
    +-- replacement workflow
    |
    v
S3StorageService
    |
    +-- createPresignedUploadUrl()
    +-- createPresignedDownloadUrl()
    +-- deleteObject()
    +-- optional objectExists()/headObject()
```

Keep AWS-specific logic out of domain controllers where practical.

---

# 27. Suggested Object-Key Builder

Centralize key generation.

Example interface:

```text
clubLogoKey(clubId)
eventBannerKey(eventId)
userProfileImageKey(userId)
```

Generated keys should:

- use trusted server-side IDs
- use UUIDs
- use allowed extensions only
- never accept arbitrary path fragments from clients

Example:

```text
events/{trustedEventId}/banners/{serverGeneratedUuid}.webp
```

# 28. API Design Guidance

Exact endpoints may follow the existing CampusVibe API style.

A suitable pattern is:

```text
POST /api/clubs/{clubId}/logo/upload-url
POST /api/events/{eventId}/banner/upload-url
POST /api/users/me/profile-image/upload-url
```

Optional confirmation endpoints:

```text
POST /api/clubs/{clubId}/logo/confirm
POST /api/events/{eventId}/banner/confirm
POST /api/users/me/profile-image/confirm
```

Deletion endpoints may be:

```text
DELETE /api/clubs/{clubId}/logo
DELETE /api/events/{eventId}/banner
DELETE /api/users/me/profile-image
```

Do not create generic arbitrary-path S3 APIs such as:

```text
POST /api/s3/upload?key=<anything>
```

That would weaken authorization boundaries.

# 29. Role-Based Media Permissions

CampusVibe has regular users, club admins, main club admins/owners, and platform admins.

Media permissions should follow existing domain permissions.

## Regular user

May:

- upload/replace/delete own profile image

May not:

- modify arbitrary club media
- modify event media unless separately authorized

## Club admin

May:

- upload/replace/delete media for their own club
- upload/replace/delete media for events owned by their club

May not:

- modify other clubs
- modify other clubs' events

## Main club admin / owner

Same media permissions as club admin unless broader club-management rules require otherwise.

No additional S3 permissions are needed at AWS level; authorization is enforced by the application.

## Platform admin

May perform platform-approved administrative media operations as defined by the application.

AWS IAM does not model CampusVibe user roles.

All CampusVibe role authorization happens inside Spring Boot.

---

# 30. AWS IAM vs Application Authorization

Do not confuse these two layers.

```text
AWS IAM
controls:
Can the backend application access S3?

Spring Security / CampusVibe authorization
controls:
Can this specific user modify this specific resource?
```

AWS sees the backend role.

AWS does not know that a CampusVibe user is a club admin.

Therefore every presigned URL request must pass application-level authorization.

---

# 31. File Security Rules

Claude Code must preserve all of the following:

- private S3 bucket
- no public object ACLs
- no public bucket policy
- server-generated object keys
- short-lived presigned URLs
- authorization before URL creation
- content-type restrictions
- upload-size limits
- least-privilege IAM policy
- no static AWS credentials
- no arbitrary client-controlled bucket/key values
- no wildcard application S3 permissions
- no presigned URLs in logs
- no permanent presigned URLs in PostgreSQL
- S3 object keys stored in PostgreSQL
- safe replacement order
- cleanup of obsolete objects
- idempotent/retry-safe cleanup where practical

---

# 32. Testing Requirements

Add unit/integration tests for at least:

## Authorization

- user cannot upload another user's profile image
- club admin can upload media for own club
- club admin cannot upload media for another club
- club admin can upload own club event banner
- club admin cannot upload another club's event banner
- unauthorized user receives 403

## Validation

- unsupported MIME type rejected
- file too large rejected
- invalid resource ID rejected
- arbitrary client key ignored/rejected

## Object keys

- keys use trusted resource IDs
- keys contain server-generated UUID
- keys use expected prefix
- path traversal strings cannot alter prefix

## Presigned URLs

- upload URL expires
- read URL expires
- generated URL targets correct bucket/key
- denied requests do not generate URLs

## Replacement/deletion

- new key saved after successful replacement
- old object scheduled/deleted only after replacement succeeds
- removing media clears database association
- cleanup failure is logged safely

Examples:

```text
400
invalid file metadata

not authenticated

403
not authorized for resource

404
club/event/user not found
```

- bucket internals unnecessarily
- IAM role details
- presigned URL signatures

# 34. Future CloudFront Migration

Do not implement CloudFront yet.

If media traffic grows, the future architecture may become:

```text
Browser
   |
   v
CloudFront
   |
   | Origin Access Control
   v
Private S3
```

Because PostgreSQL stores object keys instead of full URLs, this migration should require only service-layer URL-generation changes rather than database rewrites.

# 37. Definition of Done

The S3 media implementation is complete when:

- [ ] S3 bucket remains private.
- [ ] Block Public Access remains enabled.
- [ ] ACLs remain disabled.
- [ ] Production backend uses an EC2 IAM role.
- [ ] `CampusVibeProdMediaS3Access` is attached only to the backend role as needed.
- [ ] No application AWS access keys exist.
- [ ] Backend generates object keys server-side.
- [ ] PostgreSQL stores object keys instead of permanent URLs.
- [ ] Club/event/user authorization happens before upload URL generation.
- [ ] Upload URLs are short-lived.
- [ ] GET URLs are temporary.
- [ ] Upload types and sizes are restricted.
- [ ] User filenames are not trusted as canonical object names.
- [ ] Media replacement does not delete old media before successful replacement.
- [ ] Obsolete files can be deleted.
- [ ] Storage failures are logged without secrets.
- [ ] Presigned URLs are never logged.
- [ ] Unauthorized users cannot generate usable media URLs for write operations.
- [ ] All relevant authorization and validation tests pass.
- [ ] Production CORS allows only intended frontend origins.
- [ ] CloudFront has not been introduced unless explicitly approved.

---

# 38. Do Not Implement Without Approval

Do not introduce:

```text
public S3 bucket
public-read ACLs
public bucket policies
static AWS access keys
S3 IAM users for the application
AdministratorAccess for the backend
CloudFront
S3 Access Points
S3 Object Lambda
custom KMS key architecture
cross-account S3 access
multipart upload infrastructure
virus scanning pipeline
complex asynchronous media processing
```

These may be considered later if product or scale requirements justify them.

For the initial CampusVibe production deployment, keep the media architecture private, role-based, and presigned-URL driven.
